1. Summary

The NOMAD offseason robot is a mechanical copy of the 4414 RIPCURRENT architecture, and the released code follows the 4414 software recipe closely where 4414 has described it. The repository is small: about 5,300 lines of team-written Java in 51 files, plus two single-page HTML tools. A student could read all of it in an afternoon, which makes it a good teaching reference.

Main points
  • Architecture. Each mechanism is a WPILib subsystem that holds an enum state and resolves it to motor setpoints in periodic(). A Superstructure owns the five mechanisms and one shot solver. Commands are used only as one-line "request" wrappers for buttons and auto events. NOMAD describes this as a move from command-based to a state machine structure (Chief Delphi thread, post 1).
  • Shooting. A distance lookup table gives hood angle, flywheel RPM and time of flight. Shooting on the move uses a virtual goal that is shifted by robot velocity times time of flight, iterated up to five times. The hood and time-of-flight tables are generated by a physics calculator that ships in the repository.
  • Vision. One Limelight on the turret running MegaTag1, with turret-angle and gyro history buffers and six rejection checks. Two PhotonVision cameras are used only when the turret camera has no estimate. This matches the approach 4414 described in their binder thread (post 107).
  • Power. Current limits change with robot state and are applied on a background thread. A browser dashboard reads the logs and reports energy by subsystem, current percentiles and voltage sags.
  • Against 4414. Self-reported fire rate is similar (NOMAD 13 balls/s sustained, 4414 12 to 14). 4414's software goes further in three places it has described: a shot table optimized for tolerance to error and indexed by distance and radial velocity, tilt-compensated aiming for shooting on the bump, and autos built as state machines around drive-to-point. Season results differ widely: 4414 went 70-2 and won the Houston Championship; 6995 went 31-19 in season with a different robot, then won Beach Blitz as first seed with this one.
  • Hardware. 22 motors, all Kraken: 8 on the swerve, 5 on the intake, 3 on the dye rotor, 5 on the shooter and hood, 1 on the turret. The CAD and code confirm the 4414 layout stage by stage. NOMAD's own changes are the shooter feeder ratio, a faster turret ratio (32.5:1 against 55.7:1), gearboxes moved out of the hopper, and two CAN buses where 4414 ran one. Section 7 goes through each mechanism.
  • Gaps. The feed is not gated on flywheel speed or hood position, the turret "at setpoint" tolerance is 15 degrees, there are no unit tests and no replay logging, and the distance sensor used in autos is a stub in the public release.

5. What the code does

5.1 Superstructure and driver controls

The driver has four actions: right trigger shoots, left trigger intakes, right bumper ejects, Y takes a fixed "safe shot". On a shoot request the superstructure looks at the robot pose and picks the mode itself: PASSING if the robot is inside a rectangle that covers the field beyond x = 5 m, otherwise SCORING at the hub. The driver does not choose between scoring and passing.

The intake behavior depends on the combination of triggers: intake only runs the rollers with the intake out; shoot only runs a large in-and-out agitation to push fuel toward the rotor; shoot plus intake runs a small agitation so the intake keeps collecting. In the passing zone, shoot plus intake leaves the intake fully out.

Each loop the superstructure runs one of three solver calls (scoring, passing or idle) so that the turret always has a target, including when idle. It also gates the feed: when scoring or passing, the dye rotor is set to idle if the turret is not at its setpoint and restarted when it is.

5.2 Shot solver (ShotProjection)

  • Three tables by distance for scoring: hood angle (14 points, 1 to 10 m), flywheel RPM (12 points, 2100 to 3200 RPM), and time of flight (11 points, about 0.9 to 1.1 s). Two more tables for passing. Linear interpolation with a binary search, clamped at the ends.
  • Shooting on the move: the robot position is advanced by velocity times a 20 ms release delay, then the goal is shifted by minus velocity times time of flight. Because time of flight depends on the new distance, this is repeated up to five times or until the distance changes by less than 1 mm.
  • Outputs are turret angle relative to the robot, hood angle and RPM. The mechanisms read these through suppliers.
  • The hood table header says it was generated by the calculator in tools/ with drag off. The RPM table values are round numbers and the file does not say how they were obtained.

5.3 Turret

  • One Kraken X44 at 32.5:1, Motion Magic position control on the motor controller at 720 deg/s cruise and 3600 deg/s² acceleration, software limits at ±288 degrees about a center angle (576 degrees of travel).
  • Three wrap policies. AIM_CLOSEST picks whichever equivalent angle (±360, ±720) is nearest the current position and inside the limits. AIM_CENTRAL wraps the target to within 180 degrees of center, which leaves the most margin on both sides. UNWIND moves to the lower or upper end of travel and then returns to the previous policy; an auto event uses it to pre-position the turret before a long tracking move.
  • The superstructure switches between closest and central when the robot crosses into the passing zone, with a 0.5 s debounce.
  • No absolute encoder. The turret, hood and intake are zeroed by pressing Start while disabled, and an IsZeroed flag is published to the dashboard.

5.4 Flywheel and hood

  • Flywheel: four motors geared 1:1, one leader with three followers, velocity control with kP 0.25, kS 0.45, kV 0.1. Peak reverse voltage is 0 V, so the controller never brakes the wheel. Limits are 120 A stator and 80 A supply per motor.
  • Hood: one motor at 70.29:1, Motion Magic, range 0 to 40 degrees, 20 A stator. When the hood state is DISABLED it drives to 0 degrees instead of going neutral, so the hood is always down for the trench when not shooting.

5.5 Dye rotor (indexer)

  • One motor turns the rotor at 35:1; two motors drive the feeder wheels at 2.5:1.
  • When not feeding, the rotor turns backward slowly (30 RPM, or 90 RPM when ejecting) to agitate the hopper. 4414 describes the same idea: the rotor "constantly spins in the opposite direction slowly" (binder, Dye Rotor section).
  • A shoot request starts the feeder wheels after 0.2 s and the rotor after 0.4 s, at 2160 RPM and 120 RPM. These fixed delays stand in for a flywheel speed check.

5.6 Intake

  • Five motors: two on the main roller, one on the lower "kicker" roller, two on the rack-driven extension.
  • Six states. Rollers run on open-loop voltage. The extension is Motion Magic position control with a 20 A stator limit, which also caps the force if the intake hits a wall.
  • Agitation is a timed toggle between two extension positions: full agitation every 0.4 s until the near position is reached once, then a 5 cm stroke every 0.15 s.

5.7 Vision and localization

  • Each loop the code computes the camera pose on the robot from the turret angle, sends it to the Limelight with setCameraPose_RobotSpace, and flushes NetworkTables.
  • Pose results arrive through a NetworkTables listener that stamps them with roboRIO receive time minus the latency the Limelight reports.
  • One-second history buffers hold turret angle, the turret angle last sent to the camera, chassis yaw rate, roll and pitch.
  • An estimate is rejected if it is more than 0.4 s old, the chassis was turning at 90 deg/s or more, the robot was tilted 20 degrees or more, average tag ambiguity is above 0.3, the pose is at the origin, the turret angle at capture differs from the angle the camera had been given by more than 3 degrees, or the turret was moving faster than 180 deg/s. The last rejection reason is published as a string.
  • Standard deviations scale with distance squared and inversely with tag count. While disabled the standard deviations are 0.01, so the pose and heading snap to vision before the match.
  • PhotonVision estimates from the two side cameras are added only in loops where the turret camera has no estimate, with standard deviations from tag area and no rejection checks.
  • Limelight "rewind" capture is triggered at the end of teleop and on a button, which saves the camera's recent video for review.

5.8 Drivetrain and autos

  • CTRE Tuner X generated swerve: 7.671:1 drive, torque-current FOC drive loop, fused CANcoder steering, 120 A slip current. Teleop is open-loop voltage, field-centric, with rotation capped at 0.75 rev/s.
  • Autos use BLine: a path is a list of waypoints with a handoff radius (0.45 m default), per-segment speed limits and event triggers placed by path fraction. Follower gains are 5.0 translation and 7.0 rotation, and 0 for the third controller, which the BLine tuning guide lists as cross-track. Default limits are 4 m/s and 12 m/s².
  • Two autos are registered, a left "1 Swipe + Depot" and its mirror. Right-side paths are produced by mirroring the left-side path objects in code.
  • Path events call the same request methods the driver buttons call: start shooting, stop scoring, eject, unwind turret.
  • A warm-up routine runs a dummy path through the follower five times at startup so the first real auto loop is not slowed by first-time class loading.

5.9 Current limits, logging and tools

  • CurrentLimitManager: each "target" (intake roller, kicker, extension, drive) has a nominal limit and an apply function. Rules map a condition to tighter limits; when several rules are active the most restrictive value wins. Changes are rate-limited to one per 0.1 s per target and sent on a single background thread, because a Phoenix config call blocks until the device answers.
  • The one rule in the release: while scoring, passing or taking the safe shot, the drive supply limit drops from 42 A to 10 A per module, intake rollers to 40 A stator / 20 A supply, extension to 13 A stator. In autonomous the rules are switched off and the drive supply limit is 50 A.
  • Logging is CTRE hoot logs written to a USB stick, one per CAN bus, with pose, state names and brownout status added as custom signals. Supply current and supply voltage are logged at 20 Hz for every motor and position/velocity signals at 100 Hz; all other status frames are turned off with optimizeBusUtilization.
  • tools/dashboard.html ("NOMAD Power") opens converted .wpilog files in the browser and shows energy by subsystem, a per-motor table (peak, 50th/90th/99th percentile current, duty), a voltage timeline, and a list of voltage sags. NOMAD reported that it found inefficiencies in the kicker roller and the swerve current limits (CD post 22).
  • tools/hood_angle_calculator_1.html simulates the shot for a given exit speed, launch angle, shooter height and optional drag, scores candidate shots with adjustable weights on speed tolerance, landing margin and time of flight, and prints the hood and time-of-flight tables as Java to paste into the code.

6.3 Performance

There is no match in which the NOMAD offseason robot and RIPCURRENT can be compared directly, and 4414 did not play Beach Blitz according to its Blue Alliance page. What the sources support:

  • Throughput is about equal on paper. Both fire-rate figures are self-reported. 4414 said the shooter feeder wheels are the element that sets the rate and that the rotor is run faster than the feed needs so that balls "treadmill" briefly instead of leaving gaps. NOMAD's code runs the rotor about 11% slower than the 2.25 rev/s 4414 quoted.
  • Capacity is about equal: 80/105 against 85+/100+.
  • 4414 can shoot in conditions NOMAD's code does not cover: on the bump under defense, using tilt compensation. The NOMAD shot assumes a level robot.
  • Tuning time. 4414 said its shot system was written before the robot ran and was "mostly set and forget", with two scalars to adjust as the shooter changed. NOMAD's approach needs table edits when the shooter or the balls change, though its calculator regenerates the hood table quickly.
  • Feed gating. NOMAD gates the feed on turret position only, with a wide tolerance. How 4414 gates its feed is not stated in the sources.
  • Results. The NOMAD robot was the best robot at one offseason event. 4414 lost two official matches all season. In 4414's own words its "main competitive advantage is speed of iteration" (post 51): ten rotor versions and eleven shooter versions are shown in the binder. NOMAD's robot is the end product of that iteration, obtained by copying.

7. Hardware in detail

This section combines four sources: the 4414 binder, 4414 members' answers in the binder thread, the NOMAD thread, and the part tree of NOMAD's Onshape assembly. Where the two robots differ it says so; where only one team has described something, it is attributed to that team.

7.1 Layout and fuel path

Both robots are a ring-shaped hopper around a central "dye rotor", with a turret and shooter stacked on top of the rotor on the same axis. Fuel is collected by an over-the-bumper intake that also forms the extending front wall of the hopper. The rotor sweeps fuel from the hopper floor into a tunnel that climbs up through the middle of the turret bearing, so the shooter can spin without the feed path moving.

Speeds in the diagram are NOMAD's commanded values from the code. A 3 in wheel at 2160 RPM has a surface speed of about 8.6 m/s, and the flywheel surface runs between about 8.4 and 12.8 m/s across the scoring table.

7.3 Bumpers and hopper as structure

  • The bumper backing is 0.090 in bent aluminum and doubles as the hopper wall, which gains about 1 in of hopper width per side, and as the support for the top turret plate (binder). NOMAD called it "basically an exoskeleton" (CD post 36).
  • Side panels are bent 1/8 in polycarbonate reinforced with SRPP; hopper panels are 0.033 in polycarbonate. The front hopper wall is SRPP for weight. The rest is polycarbonate because SRPP cannot be bent (post 103).
  • Mounting is WCP bumper cones: four on the main section and two on the front for 4414. About six bolts into tapped holes on the turret plate are removed at each swap (post 113). NOMAD taps the plate 10-32, uses about ten bolts, and swaps in under three minutes with two or three people. The cones sit on top of the drive tubes, which made access hard (CD post 36).
  • 4414 first planned to leave the hopper on the robot and swap only foam and fabric, and could not make that work in time. In hindsight the whole assembly coming off "provided better access to the inside of the robot for post-match inspection & repairs" (post 113).
  • Fabric is riveted to the aluminum backing, with the holes made by a soldering iron (post 113).
  • Printed "stadium" pieces line the hopper floor and funnel fuel to the rotor. NOMAD's CAD has six of them plus printed front and rear rotor walls.
  • The net that raises capacity over the bump mounts on a separate plate so it can come off without cutting cable ties (CD post 8).

7.4 Intake

  • Rollers. A 3 in, 1/8 in wall polycarbonate main roller on two X60s at 3.45:1 and a 1.5 in lower roller on one X44 at 1.5:1. 4414 moved from shear pins to screws on the roller hubs because screws cannot slip and make roller changes faster; silicone rollers were replaced regularly (post 103).
  • Extension. Rack and pinion, 10-tooth 10DP pinions, one X44 per side at 3.33:1. It deploys at the start of the match through bumper gaps about 1.3 in wide and is held down by steel latches (binder).
  • Why two motors. 4414's first design was one motor and a belted jackshaft. Impacts made the belts slip, so they went to an all-gear drive with a motor per side. A side benefit was that one side can be pushed in while the other stays out, and 4414 would "strongly consider" independent extension again (post 103).
  • Racks. Two 1/4 in polycarbonate plates per side, left unbolted to each other so they act as a leaf spring. After the teeth chipped at the first event, both plates were given teeth to share the load, and the problem did not return. Polycarbonate was kept over SRPP out of concern for permanent deformation and wear on the teeth (post 103).
  • No crash bar. 4414 reinforced the roller instead, because a bar could fold inward and stall the roller and would fight the independent sides (post 103). Oversized bent aluminum guards let the intake slide along the field wall (binder).
  • Slides. A bearing stack guides the extension, carried over from a 2024 mechanism (post 103).
  • Wiring. A cable chain runs through one side to the near motor and wires cross the front panel to the far one (post 103). NOMAD's CAD includes an e-chain mount plate and a printed CANrange mount on the intake.
  • NOMAD specifics. An added roller keeps fuel off the rack; fuel still caught there occasionally and a fourth revision was planned (CD post 8). One or two balls can sit in the gap between the lower roller and the stadium when the hopper is nearly empty (CD posts 21 and 24). In software the extension is limited to 20 A stator, 13 A while shooting, so an impact pushes the intake in.

7.5 Dye rotor

  • Drive. One X60 turns the hook through 35:1 (36.4:1 for 4414). Two X60s drive the feeder wheels at 2.5:1 through 15 mm HTD belts and an extended gear train, a layout 4414 chose to stop belt slip (binder). NOMAD's CAD shows the bevel stage as 15-tooth to 45-tooth steel gears.
  • Wheels. 4414: a vertical 3 in omni wheel so fuel can drop onto 3 in urethane wheels, and horizontal 1.25 in goBILDA omni wheels so fuel can slide onto the ramp. NOMAD's CAD has 3 in ION omni wheels, a 3 in Stealth wheel and six 32 mm goBILDA omni wheels. 4414 bores the small omni wheels out and broaches them to 3/8 in hex (post 113).
  • Passive rollers. The hook and the ramp are lined with free-spinning rollers on bearings: 13 hook rollers and 24 ramp rollers in NOMAD's CAD. They let fuel push the fuel ahead of it and lower the current draw (binder). NOMAD used bearings with thin polycarbonate tube over them to cut friction further (CD post 8).
  • Speed. 4414 ran the rotor at about 2.25 rev/s, "about 20bps theoretical", for a measured 12 to 14 gap-free, with the shooter feeder as the regulator (post 103). That works out to about nine fuel per revolution. NOMAD's 2.0 rev/s then gives about 18 theoretical, in line with its reported 16 maximum.
  • Agitation. A "dolphin fin" ramp on the outside of the rotor and slow reverse rotation at idle relieve packing pressure. Printed "shrink wrap" covers let fuel fall around the rotor (binder).
  • Ideas 4414 did not build. A moving hopper floor geared to the rotor motor, meant to close the gaps between fuel, stayed in CAD (post 103).
  • NOMAD specifics. The rotor back piece is printed in 72D TPU, which the team found close to indestructible. 3/8 in hex inserts in the omni wheel pulleys wore badly and were replaced with all-metal 1/2 in hex parts, and a bearing plate was raised to shorten the overhang on the bevel gears (CD post 8). A 1/4-20 bolt in a tapped 1/8 in aluminum plate held without stripping. The hook has one valid assembly order, and CAD students helped build it (CD post 22). The in-season rotor motor went from an X44 to an X60 because too little power there caused jams (CD post 22).

7.6 Shooter

  • Flywheel. Four X44s at 1:1 on a 3 in wheel, all motors centered and stacked vertically. 4414 adds 1/4 in copper discs, slightly denser than steel, on top of mass discs inside the wheels (binder). NOMAD uses laser-cut steel plates, which fit well over the hex shaft (CD post 19).
  • Feeder. Three 1 in "sushi" rollers on one side, geared 16:14 from the flywheel with 0.5 in compression, and a 1 in hood roller at half the surface speed with 1 in compression (binder). NOMAD found the indexing wheel surface speed too low in testing and changed this ratio; that change is what raised its fire rate (CD post 1).
  • Motors in the ball path. The motor cans sit in the fuel path on purpose to keep the shooter low, covered with HDPE slip tape. NOMAD planned a printed ramp to bring the compression on gradually and did not get to it. The step in compression is large, and the wheel inertia absorbs it (CD post 20).
  • Hood. The pivot is coaxial with the flywheel (post 99). A 20DP sector gear in two layers of 1/8 in 7075 is driven by one X44 at 85.3:1 (70.29:1 on NOMAD). Two 6 mm wide GT2 belts run over the hood side plates to power the hood roller, held on by idlers and by tapped steel plates that act as belt guides (binder). Clearance between the hood side plates and the base is 1/8 in when stowed (post 99).
  • Size. The flywheel was moved back to make room for the Limelight in front, leaving 1.75 in of overhang over the vertical ball path (post 99). The footprint shrank a great deal between the version 6 shooter and the final one.
  • Belt widths. NOMAD's shooter CAD uses 9 mm HTD 5 mm belts. 4414 reported that a 9 mm belt skipped and stripped in one position and was replaced with gears (post 163).

7.7 Turret

  • Bearings. The lower end is a large X-contact bearing that sits on top of the dye rotor, with a second X-contact in the robot base for the rotor. Six parts capture the bearing axially and radially (CD post 34). 4414 chose X-contact bearings there because the clamping is very low profile and they are smoother and stiffer than bearing stacks (post 99).
  • Top support. Small roller bearing stacks run inside the large bore of the top turret plate, on WCP low-profile shoulder bolts. 4414 used stacks here because an X-contact bearing that large was not available and the stacks package with the turret gear and keep the cable chain high (post 99).
  • Stiffness. The shooter is supported mostly by the X-contact bearing. With the bumpers off there is a little wobble, which goes away when the bumpers and top plate are fitted (posts 99 and 113).
  • Drive. One X44. 4414 gears it 55.7:1 with a 44-tooth idler thinned to 0.275 in for cable chain clearance and double-stacked 7075 gears. NOMAD gears it 32.5:1 and moved the gearbox out of the hopper. Using a free speed of about 7,500 RPM for the X44, the top slew rate is roughly 1,390 deg/s for NOMAD and 810 deg/s for 4414; NOMAD's code cruises at 720 deg/s. NOMAD has about 58% of the torque at the turret for the same motor current.
  • Cable chain. The chain wraps around four printed corner guides. It attaches to the turret with two short bolts so the end link can flip 180 degrees as the turret passes center. Two back-to-back 8 lb constant-force springs pull a 1.625 in flex wheel to keep the chain in tension, guided by thrust bushings in a slot. Without constant tension the chain snags and breaks links when the turret whips around (binder and post 99). NOMAD's CAD has the two constant-force springs, and its code carries an unused constant for a 15 lb spring force.
  • Wiring to the turret. NOMAD runs wires from the drivebase up the back of the robot to the chain, a longer path than it wanted, with no major problems (CD post 22).

7.12 Where the code and the CAD disagree

  • Intake extension units. The code converts pinion rotations to meters with a "drum circumference" of 0.119 m. A 10-tooth 10DP pinion has a 1 in pitch diameter, which is 0.080 m per revolution. The code's full travel of 3.83 rotations is 0.31 m by the gear and 0.46 m by the code's constant, and the code separately lists the CAD travel as 0.31 m. Positions inside the code are consistent with each other, so the robot works, but every extension value labeled meters is about 1.5 times the real distance.
  • Simulation motor models. The simulation uses X60 models for the lower intake roller and the extension, where the CAD has X44s.
  • Turret inertia and spring constants are present in the code and used only by the simulation or not at all.

None of these affects the robot on the field. They matter to anyone reusing the numbers.

8. Findings in the NOMAD code

8.1 Practices worth adopting

  1. Request, then resolve. Buttons and auto events only set a state. Each subsystem turns its state into setpoints every loop with one switch. The same request methods serve teleop and auto, so there is one code path to debug. See Intake.resolveExtensionTargetPosition and the two resolve...Voltage methods.
  2. The robot picks the shot mode from its pose. One shoot button; scoring or passing is selected by field zone, and the turret wrap policy follows the zone.
  3. Turret wrap policies as named states, with an explicit unwind that autos can schedule ahead of time.
  4. Turret camera bookkeeping. Two buffers, the turret angle and the angle last sent to the camera, compared at capture time. This catches the case where the camera solved with a stale mounting pose.
  5. Named rejection reasons published for vision. A string such as "turret slewing" on the dashboard is faster to act on than a count of rejected frames.
  6. Current limits by state, applied off the main thread, with a rate limit and most-restrictive-wins merging.
  7. Signal rate discipline. Explicit update rates for every signal used, everything else disabled, supply current and voltage logged for every motor so the power dashboard has data.
  8. Checked status codes. Every config call goes through CtreUtil.reportIfNotOk.
  9. Tools in the repository as single HTML files. No install, and they stay in step with the code they generate tables for.
  10. Loop time published as current, minimum, maximum, average and overrun count over a 5 s window.
  11. Hood stows itself whenever it is not shooting.

9. Lessons for 2027

BIOCORE is released on January 9, 2027, so the game is unknown. The lessons below are the ones that do not depend on the game.

9.1 Software

  1. Use the request-and-resolve pattern for mechanisms. It works in a command-based project without a rewrite: keep WPILib subsystems, give each an enum state and a single switch in periodic(), and make commands one-line requests. It is independent of motor vendor, so it fits the Wellesley REV and AdvantageKit IO layer as it stands.
  2. Write the measured gates NOMAD left out. Flywheel within tolerance, hood within tolerance, turret within a tolerance sized to the target, then feed. With AdvantageKit inputs these are a few lines and can be unit tested.
  3. Build the scoring model before the robot exists. Both teams did this with a browser calculator. 4414's version reduced field tuning to two scalars. Whatever the 2027 scoring action is, aim for a model with one or two tunable numbers over a table with dozens.
  4. Let the robot choose modes from its pose so the driver has fewer buttons. This needs a trusted pose, which is the argument for item 5.
  5. Point the best camera at the place that matters. 4414 found a well placed camera on the main target gave more than MegaTag2 or hybrid schemes (post 107). If the camera is on a moving mechanism, copy NOMAD's two-buffer check.
  6. Treat electrical power as a design quantity. Log supply current and voltage for every motor from the first day, review energy by subsystem after each practice session, and change current limits by state. On REV controllers the equivalent of NOMAD's manager needs care: limit changes are configuration writes, so they should be non-persistent, rate-limited and kept off the main loop.
  7. Publish loop time and warm up code paths that first run in autonomous. Both are cheap and NOMAD's versions can be copied almost directly.
  8. Keep the replay and test capability Wellesley already has. It is the one area where the Wellesley sim-best-practices branch is ahead of this repository. NOMAD's code has no way to check a logic change without a robot or a simulator session.
  9. Run one autonomous routine that works with any partner. 4414 chose a single auto for three stated reasons: most time shooting, a good position at the start of teleop, and compatibility with a third robot (post 124). It also said autos "are not our strong suit". A world champion made that trade.
  10. Keep small tools as single HTML files in the robot repository. 4414's note on "single use software" (post 75) and NOMAD's two tools make the same case: a purpose-built page for one question is now cheap to produce.

9.2 Hardware

  1. Copying a proven architecture is a legitimate offseason project. NOMAD went from 40 balls at 6 to 8 per second to 80 at 13 per second. The tables in sections 6.1 and 7 show which parts were copied as-is and which were changed.
  2. Find the element that limits throughput and make everything upstream faster than it. For 4414 that was the shooter feeder; the rotor overspeeds and passive rollers let balls slip. NOMAD's fire-rate gain came from changing the feeder ratio.
  3. Reduce friction first, then add motors. Passive rollers on bearings, HDPE slip tape on non-wheel surfaces (CD post 20), and a measured power check per subsystem.
  4. Put the power where the game piece is first accelerated. Both teams found that an underpowered rotor feeder causes jams. NOMAD moved from an X44 to an X60 there in season and the final design uses two X60s.
  5. Add flywheel inertia where the game piece enters under high compression. Both robots use mass discs (copper for 4414, steel for 6995), which is why a simple velocity loop with no braking is enough.
  6. Use gears where a mechanism takes impacts or only a narrow belt fits. 4414's belted intake extension slipped under impact and a 9 mm belt in the shooter stripped; both were changed to gears (posts 103 and 163).
  7. Drive each side of an extending intake separately and let it give. A motor per side, a low current limit, and racks that flex let one side collapse under a hit without binding the other (post 103). The low stator limit in NOMAD's code is the software half of the same idea.
  8. Double up plastic gear teeth. Putting teeth on both rack plates ended tooth chipping (post 103).
  9. Use the bumpers and hopper walls as structure, and make the whole assembly removable. It adds hopper volume and stiffens the turret, and removing it opens the robot for inspection. Budget the swap: six to ten bolts and cone mounts gave NOMAD under three minutes.
  10. Stack a turret on a large X-contact bearing when the feed has to pass through its center, and use roller stacks only where a bearing of the needed size cannot be bought (post 99).
  11. Keep constant tension on a turret cable chain. 4414's spring-loaded flex wheel is a reference design. Route the wiring to the chain at the block CAD stage; NOMAD's path came out longer than it wanted (CD post 22).
  12. Split the CAN bus between the drivetrain and the mechanisms if the hardware allows. NOMAD did, and 4414 wanted to (post 72). On the 2027 SystemCore controller this is a question of which of its CAN ports each group uses.
  13. Choose materials by load case. 7075 for gears and for parts that can take a hit, TPU where a part needs to bend, polycarbonate where a part needs to spring back, stainless for thin inserts.
  14. Design for the service tasks that recur. NOMAD's separate net plate, intake removal for steer belt changes, and breaker access; tapped plates and nut strips throughout.
  15. Model the full game piece path in block CAD before detailed parts. Both teams credit it with finding interferences early (CD post 25; binder, Block CAD section).
  16. Check plates against the swerve modules before ordering, and check large one-piece plates more than once. NOMAD had to hand-cut its bottom plate (CD post 14).
  17. Keep units traceable from CAD to code. The intake extension constant in section 7.12 is the kind of error that survives because the mechanism still works. Deriving code constants from tooth counts and pitch, with the arithmetic in a comment, prevents it.
  18. Do not modify camera cabling to save space without a spare. 4414 lost two Limelights that way (post 105) and two coprocessor USB ports to a fault it could not explain (post 111).
  19. Staying under weight keeps options open. 4414 never had to trade a feature for weight and could add a thicker skid plate when it proved useful (post 99).

9.3 Process

  1. Iteration count is the difference between the two teams. 4414 names speed of iteration as its main advantage and built a parts tracker to remove small bottlenecks such as printing, shaft cutting and plastic routing (post 51).
  2. Spread ownership early. NOMAD's captain reported burnout from a small group carrying the design, and listed early ownership, clear deadlines and earlier reviews as fixes (CD post 5).
  3. Spend effort where it changes the score. 4414 skipped a turret absolute encoder and accurate zeroing because the game did not reward it, and said so. That judgment has to be made again for BIOCORE after kickoff.
  4. AI-assisted development needs structure to pay off. 4414's stated practice is state machines "easier for AI to reason about", logs supplied as context for debugging, and written skill files for recurring jobs. The tilt compensation feature came from one agent run and was verified by tests against a reference implementation (post 62).

9.4 Suggested reading order for students

  1. RobotContainer.java: the whole driver interface in 40 lines.
  2. Superstructure.java, then Intake.java: the state pattern.
  3. ShotProjection.java with tools/hood_angle_calculator_1.html open in a browser.
  4. Turret.java: wrap logic.
  5. ATVision.java: filtering and buffers.
  6. CurrentLimitManager.java with tools/dashboard.html.

10. Limits of this assessment

  • The code was read, not built or run.
  • 4414's software is described from the team's own statements; the code is not public and 4414 has said it does not plan to release its tools (post 75).
  • Fire rates and capacities are each team's own figures.
  • The NOMAD CAD was read as a part tree. No dimensions, masses or ratios were measured from the geometry; ratios come from the code and from the teams' statements. The swerve motor model is not named in the CAD tree.
  • The turret slew rates in section 7.7 assume a Kraken X44 free speed of about 7,500 RPM and ignore load.
  • The BLine controller order (translation, rotation, cross-track) is taken from the tuning order in the BLine documentation, not from the builder's API reference.
  • No EPA or other normalized scoring metric is included.
