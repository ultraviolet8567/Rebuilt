This branch takes the most recent competition code (shooter-seperate), applies every fix from the existing review branch, fixes eight more problems found while reading the code, and adds a complete desktop simulation so the robot program can be run, driven, and watched in AdvantageScope on a laptop with no robot present. A JUnit test boots the whole robot in simulation and checks that the drivetrain, gyro, flywheel, hood and intake pivot all behave. Nothing that was tuned on the robot was re-tuned. Two fixes do change on-robot behavior and are flagged below for verification.

2. New fixes found on this branch

2.1 critical Three autos would have crashed at boot once requirements were added

Shoot Left, Shoot Middle and Shoot Right run CalculatedShoot and Index in the same parallel group. With the merged fix, both require the indexer, and WPILib throws "Multiple commands in a parallel group cannot require the same subsystems" while the autos are being built, which happens in the RobotContainer constructor. The robot program would not start. The smoke test caught this on its very first run.

Fix: Index was removed from those three groups. It was redundant: CalculatedShoot already runs the indexer at the same voltage for the same duration, so the auto does exactly what it did before.

2.2 behavior change Camera pitch was sent to the Limelight as ~1.4° instead of −30°

OdometryConstants.kRotationOffset was new Rotation3d(0, -30, 0). Rotation3d takes radians, and setCameraPose_RobotSpace() takes degrees. −30 rad wraps to about 1.4 rad, which came back out of the quaternion as 1.4 and was then interpreted as 1.4°. The constant is now three plain-degree values (kCameraRoll/Pitch/YawDegrees) and −30° is what actually reaches the camera. See section 5.

2.3 fix Vision rotation was fused into the pose estimator

Standard deviation for vision rotation was 0.5. With MegaTag2 the vision rotation is derived from the gyro the code already feeds it, so fusing it lets vision fight the gyro. It is now 9 999 999 (ignored); x/y stay at 0.5. This was open item 4 in the review branch README.

2.4 fix Demo speed constants had crossed units

The linear limit was derived from the angular constant and vice versa. The derivation is corrected and swerveDemoScaleFactor set to 0.55 so the demo max speed stays at 2.75 m/s, the value that has been used at demos. No behavior change.

2.5 fix AdvantageKit was started after the subsystems were built

Logger.start() lived in robotInit(), which runs after the Robot constructor has already created RobotContainer. Logger setup now happens first in the constructor, chooses outputs by run mode (roboRIO flash on the robot, a gitignored logs/ folder on a laptop), and records metadata.

2.6 fix Kicker logged its applied output under the key KickerRunning

It now logs the boolean, and its velocity.

2.7 fix SwerveModule.getDriveVoltage() returned bus voltage, not applied voltage

The Swerve/…/DriveVoltage log entries were always ~12 V. They now show what the motor is actually being given.

2.8 fix The driver camera was opened unconditionally

On a laptop this grabs the webcam (macOS prompts for permission) or fails. CameraServer is now only started on the real robot.

3. Simulation: how it is built

The design goal was to leave the team's control code untouched and make the hardware lie convincingly. Every subsystem keeps its real motor controllers and sensors; when running on a desktop, each one also owns a small physics model and, once per loop, pushes the model's answer into the vendor's simulated device so the normal getEncoder().getVelocity(), absoluteEncoder.get() and gyro.getRotation2d() calls return believable numbers.

Swerve steer ×4DCMotorSim, NEO, 26:1Spark Max encoder and the analog absolute encoder voltageThe sim writes the exact voltage that makes getAbsoluteEncoderAngle() decode to the model's angle, offsets included.

Two REV simulation quirks worth knowing.
  1. REV's simulated Spark ignores the inverted config. That is harmless: the physics models treat "positive applied output" as "positive encoder count", which is what the real controller presents to the code.
  2. REV's simulated Spark keeps its own copy of the encoder position and overwrites the encoder with it every iterate(). So a plain encoder.setPosition() from robot code is lost in sim. Each resetRelativeEncoder() therefore also tells the sim object; on the real robot that extra line is skipped because the sim object is null. The velocity readback goes through REV's moving-average filter, like the real hardware, so it lags a few loops.

Run modes and logging

Constants.currentMode is REAL or SIM based on RobotBase.isReal(). In SIM, AdvantageKit writes .wpilog files to <project>/logs/ (gitignored) and publishes over NetworkTables so AdvantageScope can connect to localhost. Log replay was not added: it needs the IO-layer architecture that this codebase does not use.

5. Things to verify on the real robot

  1. Camera pitch (2.2). The Limelight now receives pitch = −30°. Confirm the sign matches how the camera is physically mounted (Limelight convention: positive pitch = tilted up). If MegaTag2 poses jump when the robot is stationary, try +30. The old code was effectively sending ~0°.
  2. Vision rotation ignored (2.3). Heading now comes from the gyro alone. Expected to be an improvement; watch Odometry/Pose vs Odometry/GyroHeading.
  3. Auto files (2.1). The three Shoot autos should behave identically. Run one in the pit to confirm the indexer still runs during the shot.
  4. Requirements (section 1). Operator button combinations that used to overlap (e.g. Feed + SetPivot) now cancel each other. This is intended but it is a feel change for the operator.

6. Open items deliberately not changed

  • Pivot absolute encoder window. With the current offset the absolute encoder only decodes pivot angles in roughly (−1.9, 0.62] rad. Stowed (0.1) is inside; deployed (2.0) aliases to about −0.5. The code copes because it only re-syncs when the two encoders agree within 0.1 rad, but if the robot is powered on with the intake deployed, the relative encoder is seeded wrong and the pivot will drive to the wrong place. Same shape of issue for the hood above 0.278 rad. Fix needs the robot: re-measure offsets, or move the encoder to the output shaft.
  • Follower flywheel PID negation. Correct only if the follower encoder reads negative during a shot; check Shooter/Flywheel/Follower/Velocity in a log.
  • Shooter lookup table decreases beyond ~5 m (TODO in code).
  • Slew-rate limiters remain disabled in ManualTeleOp.
  • Log files on roboRIO flash (/home/lvuser/logs) still need periodic cleanup.
  • Log replay is not available (see section 3).
