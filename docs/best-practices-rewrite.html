Rewriting the simulation branch against what the top teams actually do

What changed on claude/sim-best-practices-rewrite, which piece of evidence drove each change, and what it buys the robot.

base: sim/shooter-seperate-sim @ 1135251  ·  87 files, +4913 / −3864  ·  ./gradlew build and ./gradlew test pass (15/15)

This branch is not a tidy-up. It is a reimplementation of the same robot behaviour on a different skeleton, driven by a survey of the robot code that 45 of the highest-performing 2026 FRC teams published. Along the way the survey exposed several defects in the old code that would have cost points on the field — the largest being a shooter that deliberately slowed down the further it stood from the hub.

1. Method: how the corpus was used

The code-finder tool in ~/Documents/home related/FRC/FRC2026/code-finder ranks teams by Match13 xp, finds each one's 2026 robot repository through GitHub code search and Blue Alliance, verifies it by reading wpilib_preferences.json, scores the candidates and clones the winner. Its repos/2026/ directory held 45 repositories; 42 of them are Java robot projects (the other three are a Python robot, a strategy tool, and an empty code bank).

Rather than reading a handful of repositories and copying whichever one looked nicest, every candidate practice was counted across all 42. A practice that 34 teams use is a convention; one that 6 teams use is a preference. The counts below are what decided each change, and each change in section 3 and 4 names the count that drove it.

Two repositories were read closely because they are the nearest architectural relatives of this robot: FRC 6002 "TriShooter" (REV Sparks, AdvantageKit IO layer, a hood/kicker/conveyor shooter for the same game) and FRC 341 (the most complete IO-layer and vision-filtering implementation in the set). Where a specific file was used as a model, it is named.

2. The shape of the change

The file layout follows from that. Mechanism constants moved next to their mechanism (41 of 42 corpus robots organise this way), and the 15 single-purpose Command subclasses collapsed into factory methods on the subsystems that own the hardware.

3. Changes that affect how the robot plays

3.1 The shooter range curve performance

Source: 34 / 42 — interpolating lookup table for distance→velocity. Models: 341/subsystems/shooter/ShooterConstants.java, 10021/subsystems/flywheel/FlywheelConstants.java.

The old code computed the flywheel setpoint from a fitted quadratic:

beforereturn 1310.13 + 1270.33*dist
       - 128.09*dist*dist;
afterreturn ShooterConstants
  .kDistanceToRpm.get(distanceMeters);

That parabola opens downwards. It peaks at 4.96 m and then falls away, so past five metres the further the robot stood from the hub, the slower it spun the wheel. At eight metres it commanded 3275 RPM — less than it commanded at two metres. Every long shot undershot, and the undershoot grew with range.

Why a table and not a better polynomial. A table cannot turn over, it clamps rather than extrapolating when asked for a distance outside its range, and new range-test points can be pasted in without anyone refitting anything. That last property is why 34 of 42 teams use one: the table is edited by the students who ran the range test, in the units they measured.

The regression is now a test, not a comment:

@Test void shooterRangeTableIsMonotonic() {
    for (double d = 1.0; d <= 9.0; d += 0.25)
        assertTrue(Flywheel.rpmForDistance(d) >= previous, ...);
}

3.2 The flywheel had no feedback term performance

Source: found while porting; confirmed against the 36 / 42 that run a real closed loop on velocity. Measured in the new simulation.

kFlywheelP was 1e-5. The PID takes RPM in and produces volts out, so a 100 RPM error produced a one millivolt correction. The loop was feedforward-only in everything but name: whatever offset kV left behind stayed there forever, and — the part that costs points — the wheel had no way to recover the speed it loses as a ball passes through it. The next ball left at whatever velocity the wheel happened to have drooped to.

The new simulation makes this measurable. Commanded 3000 RPM, the two wheels settled at 3081 and 3115 RPM — outside the 100 RPM tolerance that gates the kicker, and never converging. Raising kFlywheelP to 0.002 V/RPM (0.2 V at the ready tolerance, ~1 V at 500 RPM error, well inside the 10 V clamp) brings both under 55 RPM.

3.3 "At speed" was one-sided, and only watched one wheel performance

Source: the corpus convention is a symmetric tolerance on every driven wheel; FRC 341 gates its uptake on TOLERANCE_RPM either side.
beforereturn Math.abs(getVelocity(leadMotor))
  > Math.abs(velocity) - tolerance;
afterreturn |lead − setpoint| < tol
  && |follower − setpoint| < tol;

Two consequences. An over-speeding wheel read as ready, so the kicker would feed while the shooter was still above its setpoint. And only the lead wheel was checked, so a follower that had not caught up — or that was fighting a jam — never blocked the shot. A ball fed into a shooter whose two sides are at different speeds leaves with side spin that no range table accounts for.

Test atSpeedRejectsOverspeed now pins this: spin to 1000 RPM, drop the setpoint to 200, and assert that the shooter does not report ready while it coasts down through the target.

3.4 Motor inversion moved into the controller configuration architecture

Source: 37 / 42 set inversion in the motor config. 0 / 42 negate at the call site — the clearest unanimous result in the whole survey.

Five subsystems negated the voltage just before writing it:

before — five placesvoltage *= kFlywheelInverted ? -1 : 1;
motor.setVoltage(voltage);

// ...and so the measurement
// had to be negated too:
pid.calculate(-getVelocity(lead), target)
afterconfig.inverted(kFlywheelInverted);
motor.setVoltage(voltage);

// command and measurement now
// share a sign:
pid.calculate(inputs.leadVelocityRpm, target)

Negating at the call site flips the command but not the encoder, so the measurement and the setpoint end up in opposite sign conventions and the discrepancy has to be patched at the feedback input. That is exactly the -getVelocity(leadMotor) in the old flywheel loop. Setting inverted in the configuration flips both together and the minus sign disappears.

The hood benefited twice over: it had two constants, kHoodInverted (negate the command) and kHoodRelativeEncoderInverted (negate the measurement), describing one physical fact — which way round the motor is bolted in. They had to be kept equal by hand, and setting one without the other turns the position loop into positive feedback that drives the hood into its hard stop. They are now one flag. The same pair on the pivot collapsed the same way.

Net motor direction on the field is unchanged.

3.5 Drive wheels are closed-loop, cosine-scaled, and discretised performance

Sources: closed loop 36 / 42; cosine scaling 26 / 42; ChassisSpeeds.discretize 18 / 42. Model: 6002/subsystems/drive/Module.java and io/ModuleIOSpark.java.

Closed loop

Modules were driven open loop: driveMotor.set(speed / kPhysicalMaxSpeed). That is a duty cycle, and it only produces the requested speed on a full battery with no load. Under a sagging battery, or while pushing another robot, the wheel turned slower than the kinematics assumed — so odometry over-counted distance and PathPlanner paths came up short exactly when the match was hardest. The Spark now runs a velocity loop with kS/kV feedforward.

Cosine scaling

While a module is still rotating toward its commanded angle, any speed it is given pushes the robot sideways. state.cosineScale(currentAngle) scales the commanded speed by the cosine of the remaining steering error, so the wheel waits until it is roughly pointed the right way before it pushes hard. Visible effect: the robot stops lurching off heading at the start of a hard direction change.

Discretisation

Swerve kinematics assume the robot travels in a straight line for the whole 20 ms loop. When it is translating and rotating at once the real path is an arc, so the robot drifts perpendicular to its motion — and the odometry, using the same flawed assumption, does not notice. One call to ChassisSpeeds.discretize corrects it.

And the X-lock is now actually an X

before45°, 135°, −45°, 45°
← back two wheels parallel
aftereach wheel points along its own
chassis-corner vector — correct
by construction

The old angles left the two back wheels parallel, which is a parallelogram: the robot could still be shoved sideways while "locked". Test xLockPointsWheelsAtTheChassisCorners checks the geometry.

3.6 Heading hold: a controller instead of four hand-written branches performance

Source: 34 / 42 enable continuous input on the heading controller; 16 / 42 use a dedicated profiled heading controller. Model: 341/commands/DriveCommands.java :: joystickDriveAtAngle.

DriftTeleOp worked out the shortest way round by hand:

if (target < heading) {
    if (heading - target < Math.PI) turningSpeed = -pid.calculate(heading, target);
    else                            turningSpeed = -pid.calculate(heading, target + 2*Math.PI);
} else {
    if (target - heading < Math.PI) turningSpeed = -pid.calculate(heading, target);
    else                            turningSpeed = -pid.calculate(heading, target - 2*Math.PI);
}

Four branches, two sign conventions (heading came from getHeading().unaryMinus() while target did not), and a mapping into [0, 2π) that has to agree with both. A ProfiledPIDController with enableContinuousInput(-π, π) does the same thing correctly by construction, and the trapezoid profile on top means the robot slews to a new heading at a bounded rate instead of jerking at whatever the proportional term produces.

3.7 Vision is filtered and weighted performance

Source: 34 / 42 scale standard deviations by tag count and distance; 37 / 42 tune them at all. Model: 341/subsystems/vision/Vision.java.

Every MegaTag2 result went straight into the pose estimator at a fixed (0.5, 0.5, ∞). A single tag glimpsed edge-on across the field moved the pose estimate exactly as hard as two tags two metres away. That is the mechanism behind "the robot teleports on the field display", and behind auto-aim snapping to a wrong heading.

Every rejection is logged with its reason at Vision/RejectReason, so a post-match review can tell "the camera saw nothing" from "we threw it all away".

Two mounting-geometry bugs were also carried into the new VisionConstants with the reasoning attached: the camera pitch had at one point been wrapped in a Rotation3d (which takes radians) before being handed to a Limelight API that takes degrees, so a −30° mounting angle arrived as 1.4° and every range the camera computed was wrong.

3.8 Field-relative driving on the red alliance performance

Source: read while porting; the corpus convention is a 180° heading rotation, e.g. 6002/commands/drive/DriveCommands.java.
beforeAllianceFlipUtil.apply(heading)
// = new Rotation2d(-cos, sin)
// i.e. MIRRORED about X
afterheading.plus(Rotation2d.k180deg)
// i.e. ROTATED half a turn

AllianceFlipUtil.apply(Rotation2d) mirrors a rotation. That is the right operation for flipping a field position to the other alliance's side, and the wrong one for converting a driver's "forward" into field coordinates: mirroring inverts the sense of one axis, so on red the robot's response to sideways stick was reversed relative to blue. A half-turn rotation is what "forward is away from your own wall" actually means.

3.9 Joystick shaping performance

Source: 23 / 42 use MathUtil.applyDeadband; the nine that shape a drive stick all apply it to the vector magnitude, then square. Model: 341, 1768, 10021, 6002 — identical code in all four.
beforexSpeed *= (xSpeed > 0) ? 1/0.8 : 1/0.9;
ySpeed *= 1/0.9;
if (|xSpeed| < db) xSpeed = 0;
if (|ySpeed| < db) ySpeed = 0;
afterdouble m = applyDeadband(hypot(x,y), db);
Rotation2d dir = new Rotation2d(atan2(y,x));
m = m * m;

Per-axis deadbands carve a cross out of the stick's travel: a diagonal push of 0.1 in each axis produces nothing at all, and a stick slightly off-centre on one axis distorts every diagonal. Deadbanding the magnitude carves a circle, which is the shape of the physical dead zone.

The three scale factors are gone too. 1/0.8 forward against 1/0.9 backward made the robot 12% more sensitive pushing away from the driver than toward them, for no recorded reason. Squaring the magnitude gives fine control near centre and full speed at the rim, which is what those factors were probably reaching for.

3.10 Autonomous selection cannot name a routine that does not exist reliability

Source: the corpus universally uses one chooser of real Command objects, most commonly AutoBuilder.buildAutoChooser().

The old chooser had two dropdowns and pasted their selections together into a string — "Shoot" plus "Left" made "Shoot Left" — then looked that string up in a map. Most of the nine combinations named nothing, and choosing one returned null from getSelectedAuto(), which autonomousInit() quietly skipped. The failure mode was a robot sitting still for fifteen seconds with nothing on the dashboard explaining why.

One chooser built from the .auto files that are actually deployed cannot express an invalid selection. A renamed routine disappears from the dashboard instead of becoming a selection that fails at match start, the choice is recorded into the log, and an unselected chooser raises an Alert and returns a named do-nothing command rather than null.

4. Changes that affect how the code is worked on

4.1 The IO layer, and log replay architecture

Source: 22 / 42 IO interfaces, 19 / 42 @AutoLog, 19 / 42 a REPLAY mode. Model: 6002 (Spark-based, same shape of robot) and 341.

Each subsystem now reads its sensors through an interface whose fields are annotated @AutoLog. AdvantageKit generates a companion class that writes every field into the log each loop and, in REPLAY mode, reads them back out. Set Constants.kSimMode = REPLAY, point it at a match log, and the same subsystem code runs against exactly the inputs it saw on the field — with whatever control changes are checked out now. A shooter mis-fire from a match can be debugged, and the fix verified, without the robot being powered on.

The simulation implementations are a second, independent win. They talk to no vendor code at all. The previous simulation drove REV's SparkFlexSim/SparkMaxSim shims, so every quirk of that library leaked into files that also run on the real robot:

  • iterate() ignores the configured inversion;
  • it overwrites the encoder position with its own copy, so resetEncoders() had to poke the sim object as well — a line of simulation code sitting inside a real-robot method;
  • it low-pass filters the velocity it hands back, so simulated control loops saw a different plant than real ones.

Behind an interface, the simulation is an honest motor-and-gearbox model with its own controllers, and the real-robot classes keep no simulation code whatsoever. All three workarounds are gone.

4.2 Faults are reported where someone will see them reliability

Source: 20 / 42 use WPILib Alert; 22 / 42 debounce device connection. Manager modelled on 6002/utils/AlertsManager.java; Spark helpers on FRC 6328's SparkUtil.

The old code reported problems with System.out.println at construction time, which scrolls off the RioLog long before a match starts and never reaches the driver station. An Alert is a persistent named condition: it shows on the dashboard for as long as it holds and clears itself when it stops.

Alerts now exist for every drive motor, steering motor, steering encoder, flywheel, hood, pivot, funnel, indexer and kicker disconnect; the gyro; the camera; brownout; low battery; CAN receive errors; an unselected auto; and tuning mode being left on. The LED strip flashes red whenever any error-level alert is active, so the fault is visible from across the pit.

Underneath, Spark reads go through SparkUtil.ifOk. A failed CAN read does not throw — it returns a stale or zero value and sets an error code that nothing was checking. A steering encoder quietly returning 0.0 means the module confidently steers "straight ahead" and the robot drives into a wall. Now a failed read raises a sticky fault, a Debouncer turns a half-second of failures into a disconnect, and the driver sees it. Configuration is retried up to five times, because it routinely fails once at boot while the CAN bus is still enumerating.

4.3 The LED strip is no longer a global variable architecture

Source: 11 / 42 keep an explicit RobotState (341, 6002, 3467).

Lights was a singleton with eleven public mutable fields that half the robot wrote into and the other half read back. Swerve.getMaxSpeed() asked the light strip whether demo mode was on; Flywheel.getTargetVelocity() did the same. The LED class sat on the dependency path of the drivetrain's top speed.

Those facts now live in RobotState, named for what they are. Leds became an ordinary subsystem that only reads it — and being a subsystem, the scheduler runs it, so it is no longer called by hand from robotPeriodic().

One real bug fell out of the move. Demo scaling used to be applied by assigning the demo constant back into targetVelocity inside the getter, so the next loop found the distance-based velocity replaced by the constant — the robot kept shooting at demo speed for the rest of the match. Scaling on the way out preserves the commanded value; test demoModeScalesButDoesNotClobber holds it there.

4.4 Commands are factories on the subsystem that owns the hardware architecture

Source: 37 / 42 use inline subsystem factories; 34 / 42 use Commands.*.

Fifteen Command subclasses — Shoot, DirectShoot, SpinIntake, SpinIndexer, SetPivot, SetHood, ManualKicker, RunKicker, Feed, Shuffle, CalculatedShoot, ResetPivot, CorrectAuto, and the two teleop drive classes — each wrapped one or two lines of behaviour in forty of boilerplate. Two were entirely empty. They are now methods next to the hardware they command.

Three behavioural fixes came with the collapse:

  • Stale writes. SpinIntake and Shoot wrote their output once, in initialize(). A Spark that has not heard from the roboRIO for 100 ms cuts output on its own watchdog, so a long intake could stall silently until the button was released and pressed again. The factories use runEnd, which writes every loop.
  • Ownership. SetPivot set its target in initialize() and finished immediately, releasing the requirement while the arm was still moving; a second binding could take over mid-motion. Pivot.goTo() holds the requirement for as long as the button is held.
  • Loop-counted timing. Feed shook the intake using count % 50 > 25, baking the loop period into the behaviour. Pivot.shake() uses the FPGA clock and a period in seconds.

The kicker interlock also moved to where it cannot be forgotten: the kicker's default command feeds when and only when both flywheels are at speed, so every shooting command inherits it instead of having to remember it.

4.5 Loop timing and disable behaviour reliability

Source: 12 / 42 raise thread priority around the scheduler.
  • The scheduler runs at real-time priority 99 and drops back to 10 afterwards. Everything else on the roboRIO — the web server, CAN receive threads, garbage collection — can otherwise delay the control loop, and a control loop that runs late is one with the wrong dt.
  • Tunable-number gains are only pushed into controllers when a value actually changes. The old flywheel and pivot wrote all seven gains into their controllers fifty times a second regardless.
  • Drive motors coast three seconds after the robot is disabled, so it can be pushed off the field — but not instantly, because a robot disabled at speed would keep rolling.
  • silenceJoystickConnectionWarning, so warnings about unused joystick ports stop hiding the ones that matter.

6. What was deliberately left alone

Five widely-used practices were surveyed and not adopted. Each is a real improvement; each was judged to cost more than it returns right now, and all five are listed here so the decision is visible rather than silent.

PracticeCorpusWhy not now
WPILib Units library39 / 42 A large mechanical migration with no behavioural benefit, and every conversion touched is a chance to introduce exactly the unit bug the library exists to prevent. Worth doing at the start of an off-season, not on top of a rewrite this size.
Motion profiling on hood and pivot39 / 42 Both still run plain PID plus feedforward. Adding a trapezoid profile changes how they move and therefore needs re-tuning on the real mechanism. The heading controller is profiled (§3.6) because it was being rewritten anyway.
SysId characterisation31 / 42 Needs hardware time to run. The one characterisation that can be run in a few seconds on a patch of carpet — wheel radius — was added, and is on the auto chooser (see below).
Superstructure state machine30 / 42 This robot has one shooter, one intake and one indexer with no conflicting geometry. A state machine would add a layer without removing a problem.
High-frequency odometry thread15 / 42 Genuinely valuable, and the right next step. It needs careful threading work, and the steering encoders here are analog inputs read by the roboRIO rather than CAN signals that can be queued, so it is not a drop-in of the template version.

Two things left empty on purpose

The hood range table. ShooterConstants.kDistanceToHoodAngle exists and is empty. The robot has never been range-tested for hood angle — the hood goes to a fixed position and the operator trims it — so there is no data to put in it, and inventing numbers would change how the robot shoots on the field on the strength of a guess. Hood.angleForDistance() falls back to today's fixed position while the table is empty; add measured pairs from a range session and the fallback stops being used, with no other code change.

The wheel-diameter fudge factor. Units.inchesToMeters(3.95) * 1.613 / 1.664 was kept exactly as it was, because changing it would change every distance the robot believes it has travelled. What was added is the routine that produces that number: DriveCommands.wheelRadiusCharacterization, on the auto chooser. Spin in place for twelve seconds on clear carpet and it prints the measured radius. Re-run it whenever the tread is replaced, instead of guessing.

7. Two carried-forward notes for whoever works on this next

Two pieces of accumulated history were preserved verbatim rather than cleaned up, because their exact values matter and their provenance is the useful part:

  • Encoder offsets. kAbsoluteEncoderOffsetsRad, kHoodEncoderOffsetRad and kPivotEncoderOffsetRad are still written as the running sum of every field recalibration the team has done (2.15 + 3.05 + 0.01, and so on), because collapsing them to a single decimal would lose the trail and risk a rounding change in a value that is applied modulo 2π. Each now carries a comment saying how to re-measure it, and the raw analog voltage is logged at Drive/Module{n}/AbsoluteEncoderVolts so it can be re-measured from a match log rather than from the pit.
  • Absolute-encoder aliasing. Both the hood and the pivot have their absolute encoder geared before the final reduction, so each only reads unambiguously over a window — about 2π/16.8 rad of hood travel, 2π/2.5 rad of pivot travel — and aliases to a plausible but wrong value outside it. That is why both subsystems only re-seed the relative encoder when the two readings are close. The simulation reproduces the aliasing rather than hiding it, precisely so that this code path is exercised.
